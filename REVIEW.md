# REVIEW.md

List every defect found in the starter `app/main.py`. For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `GET /health` | Returns `{"status": "ok"}` unconditionally without ever pinging MongoDB. The contract requires 503 when MongoDB is unavailable. | Kill MongoDB and call `GET /health` — still returns 200. | Wrapped `client.admin.command("ping")` in a try/except; return 503 on failure. |
| 2 | `POST /employees` — race condition | Uses a check-then-insert pattern (`find_one` then `insert_one`). Two concurrent requests with the same `emp_code` can both pass the check and both insert, violating the uniqueness guarantee. | Send two simultaneous POST requests with the same `emp_code`. Both return 201. | Removed the pre-check; rely solely on the unique index and catch `DuplicateKeyError` from `insert_one`. |
| 3 | `POST /employees` — `created_at` stored as naive local time | `datetime.now()` returns a naive datetime in the server's local timezone. The contract and data model require UTC BSON datetimes. On a server not in UTC this stores the wrong instant and `dt_to_ms` produces the wrong epoch value. | Compare `created_at` in the response against wall-clock UTC — they differ by the server's UTC offset. | Changed to `datetime.now(tz=timezone.utc)`. |
| 4 | `GET /employees` — wrong `skip` calculation | `skip = page * page_size` skips one extra page. Page 1 should skip 0 rows but skips `page_size` rows instead; every page is off by one. | `GET /employees?page=1` — first `page_size` employees are missing from the response. | Changed to `skip = (page - 1) * page_size`. |
| 5 | `GET /employees` — `total` ignores the `department` filter | `count_documents({})` always counts the whole collection. When `?department=Sales` is passed, `total` reports the headcount of all departments, not just Sales. | Create employees in two departments; filter by one — `total` is wrong. | Changed to `count_documents(q)` where `q` is the already-built filter. |
| 6 | `GET /employees` — results not sorted by `emp_code` | `find(q)` with no `.sort()` returns documents in natural (insertion) order. The contract requires ascending `emp_code`. | Insert employees out of alphabetical order; the list comes back unsorted. | Added `.sort("emp_code", ASCENDING)`. |
| 7 | `POST /attendance/punch-in` — no 404 when employee not found | After `find_one` the code uses `emp["shift_start"]` without checking whether `emp` is `None`. If `emp_code` is unknown, this raises `TypeError: 'NoneType' object is not subscriptable`, which FastAPI surfaces as a 500. | POST punch-in with an unknown `emp_code` — 500 instead of 404. | Added `if not emp: raise HTTPException(404, "employee not found")`. |
| 8 | `POST /attendance/punch-in` — punch-in race condition | Uses check-then-insert: `find_one` to check existence, then `insert_one`. Two concurrent punch-ins for the same employee and date can both pass the check and both insert. | Send two simultaneous punch-ins for the same employee — both return 201. | Removed the pre-check; rely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError`. |
| 9 | `compute_late_minutes` — wrong late threshold | Compares `minutes > 10` (integer minutes) instead of checking elapsed seconds against a 600-second grace period. A punch-in at exactly shift_start + 10 min 01 s gives `minutes = 10` (floor), which passes `> 10` as false — but per R2 it should be late (elapsed = 601 s > 600 s). Conversely, 09:40:00 on a 09:30 shift gives `minutes = 10` and `> 10` is false — correct — but only by coincidence of integer truncation. The rule is "strictly more than 10 minutes", meaning > 600 seconds. | Input: shift 09:30, punch-in 09:40:01. Expected `late_minutes = 10`. Starter returns 0. | Rewrote to use `int((ist - shift_start_dt).total_seconds())` and compare `elapsed_secs <= 600`; return `elapsed_secs // 60` when late. |
| 10 | `compute_late_minutes` — no timezone handling | Builds `start` by calling `punch_in.replace(hour=h, minute=m, ...)` on a naive datetime and then computes a timedelta. If `punch_in` is stored/passed as UTC and the shift time is IST, the difference is wrong by 5 h 30 m. | An employee with shift 09:30 IST who punches in at 09:28 IST (UTC 03:58) — the naive computation compares 03:58 UTC against a "09:30 UTC" reference, yielding a large negative, and `minutes` becomes a large negative → returns 0 by accident. | All calculations now done in IST: convert `punch_in` to `IST`-aware before building the shift-start reference time. |
| 11 | `compute_work_hours` — wrong rounding | Uses `round(..., 2)` which applies banker's rounding (round-half-to-even). R4 requires half-up rounding. Example: 7.255 hours → banker's rounds to 7.25, half-up gives 7.26. | Compute work hours for a shift where the exact midpoint falls on .5 ms. | Replaced with `half_up(diff / 3600, 2)` using `Decimal` with `ROUND_HALF_UP`. |
| 12 | `compute_overtime` — wrong shift-end datetime construction | `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` mixes a naive date parse with `tzinfo=IST`, which sets the fold/offset without converting. For overnight shifts `shift_end` is on the next calendar day but the code uses `date_str` (the punch date) without adding a day. | Employee with overnight shift 22:00–06:00; punch-out at 06:40 IST next day. Expected overtime 40 min. Starter computes a shift_end of 06:00 on the same calendar date as punch-out, yielding wrong or negative overtime. | Rewrote: detect overnight (`shift_end <= shift_start`), add `timedelta(days=1)` to the base date for overnight shifts, then attach `tzinfo=IST` properly. |
| 13 | `POST /attendance/punch-in` — no epoch-ms validation | `punched_at` is typed `Optional[int]` with no range check. A client passing seconds-level timestamps (e.g. `1720000000`) is silently accepted and stored, giving wrong dates. A float or string is rejected by Pydantic but a seconds-level int is not. | POST with `"punched_at": 1720000000` (looks like seconds) — accepted, attendance date computed from the wrong era. | Added a validator that rejects values below `100_000_000_000` (the lower bound that distinguishes ms from seconds) with a 422. |
| 14 | `POST /attendance/punch-in` — attendance date ignores IST and overnight shifts | `ts.date().isoformat()` uses the datetime's own timezone (or naive local time) to get the calendar date. It does not implement R1: IST conversion and overnight-shift logic. A punch at 00:15 UTC (05:45 IST) would be attributed to the previous UTC date, not the correct IST date. Overnight shifts are completely unhandled. | An employee with overnight shift 22:00–06:00 punches in at 23:50 IST (18:20 UTC). Starter attributes the record to the UTC date (previous day). | Extracted `attendance_date_for_punch()` that converts to IST and handles the overnight exception (punch before shift_end → previous day). |
| 15 | `GET /attendance` — loads entire collection into Python | `list(db.attendance_logs.find(q))` fetches every matching document before sorting and slicing in Python. On 100 k documents this is slow and memory-intensive. `total = len(docs)` also counts the filtered set twice (once fetched, once counted). | Load 100 k records and call the endpoint — high latency and RAM spike. | Replaced with `count_documents(q)` for the total, and `find(q).sort(...).skip(skip).limit(page_size)` to let MongoDB do the work, backed by the compound index. |
| 16 | `GET /attendance` — `_id` leaked in response | `d["id"] = str(d.pop("_id"))` renames `_id` to `id` and returns it. The contract's `AttendanceRecord` schema has no `id` field; `_id` must never appear in responses. | Call the list endpoint — each record contains an unexpected `id` field. | Project `{"_id": 0}` in the `find()` call and strip `_id` in `fmt_attendance()`. |
| 17 | No indexes created at startup | The starter has no `create_index` calls. All queries hit a full collection scan. At 100 k documents, every endpoint is slow and the `(emp_code, date)` uniqueness guarantee is not enforced at the database level, so the race-condition fix in #2/#8 is also incomplete without a unique index. | Start the app; run `db.attendance_logs.getIndexes()` — only `_id` exists. All queries show `COLLSCAN` in explain output. | Added a `@app.on_event("startup")` handler that creates all required indexes idempotently: unique index on `employees.emp_code`, compound unique index on `attendance_logs.(emp_code, date)`, and sort/filter indexes for list and analytics queries. |

## Things examined and decided were NOT defects

- **`IST = timezone(timedelta(hours=5, minutes=30))`** — correct UTC+05:30 definition.
- **`body.model_dump()`** — Pydantic v2 method, appropriate for the declared dependency `pydantic>=2.6`.
- **`load_dotenv()` at module level** — acceptable; real environment variables still take priority because `python-dotenv` does not overwrite already-set variables by default.
- **`Optional[int]` for `punched_at`** — correct typing; the field is genuinely optional (defaults to now).
